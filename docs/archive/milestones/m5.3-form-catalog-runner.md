# M5.3 form catalog and thin runner

## Refresh and cache

The **Forms** screen reads only the local catalog on mount. A Central request is
made only after the user presses **Refresh forms**. The composition service uses
the public App User/OpenRosa client surface exclusively:

1. `listForms()`
2. `getFormManifest({ formId })`
3. `downloadForm({ formId })`
4. `downloadFormAttachment({ formId, filename })`

It does not construct or consume an advertised download URL. Manifest
`downloadUrl` and `integrityUrl` values can contain the App User key, so they are
neither stored nor sent to the UI.

Migration 3 stores mutable `forms` catalog metadata, immutable `form_versions`,
and immutable `form_resources`. Form XML, sanitized manifest metadata, and every
attachment are atomically written through `gather-storage` using durable
project-relative keys. A form-version identity includes the form listing version
and hash plus a sanitized manifest fingerprint. Thus a changed `plants.csv`
token creates a new immutable version instead of replacing resources used by a
draft. SQLite triggers reject updates to version/resource rows; the catalog
repository itself issues only `INSERT OR IGNORE` for those rows.

## Runner

`FormRunner` mounts `WebViewXFormsHost` and its hidden sidecar via the public
`odk-xforms-webview` API. It owns the form-running lifecycle and delegates
engine-node rendering to `src/xforms/XFormsRenderer.js`. Cached resources are
passed to the public `loadForm(xml, attachments)` hook action.

`XFormsRenderer` maps the engine's ordered `FormRenderModel` directly, with
current values, relevance, requiredness, readonly state, constraints, choices,
and calculations read through the existing granular `odk-xforms-react` hooks.
Its controls use reusable presentation components that do not know XForms
references or engine state. It supports text, integer, decimal, notes,
select-one, select-multiple, Entity List choices, calculated/read-only fields,
groups, add-repeat controls, and image capture. Controls outside that surface
are explicitly identified as unsupported rather than approximated. The render
model exposes no explicit Entity source, so Entity List choices have no
UUID-derived cosmetic badge. The compact Form Outline is only an ordered
projection of the engine render model.

## Verification

- Offline unit tests: `npm run test:unit`
- Optional live App User check:
  `node --test test/live/form-catalog.live.test.mjs`
- Android-only cached Entity List gate:
  `scripts/run-android-gate.sh 'M53_CATALOG_RUNNER_RESULT::' .gate-logs/m53-catalog-runner.log 1200`

The Android gate writes/reads fixture XML, manifest metadata, and `plants.csv`
through real durable storage (also applying migration 3), then verifies choices
from that attachment, selects a UUID, and asserts engine-calculated
site/block/plant-code values. Restore `index.js` to `App` and remove
`.gate-logs/` when finished.
