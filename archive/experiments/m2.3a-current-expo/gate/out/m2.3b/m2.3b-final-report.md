## On-device runtime validation (follow-up)

The bundle/bytecode/Node-semantics results above were later validated by actually
launching the app on a running emulator. This changed the picture and the sections
above should be read together with this addendum.

### Setup
- Android: `Pixel_3a_API_34` emulator (API 34, Android 14), debug build via
  `M23B_XFORMS_MODE=compat expo run:android`, Metro serving the compat-aliased bundle.
- App entry installs the slimdom DOM compatibility layer **before** the engine module
  is evaluated (`src/installDomFirst.js`, imported first in `index.js`). This is
  required because React Native defines a global `window`, and the engine's bundled
  web-tree-sitter glue reads `window.document.currentScript` during parser init at
  module-evaluation time.

### Results (Android, Hermes)
- Metro bundling in compat mode: **PASS** (716 modules, no TLA error).
- Hermes execution reached (`HermesInternal` present): **PASS**.
- TLA compatibility transform: **PASS** (module evaluated; no top-level-await error).
- DOM `currentScript` init (after ordering fix): **PASS**.
- slimdom compatibility init step: **PASS**.
- `loadForm(...)`: **FAIL** — `ReferenceError: Property 'WebAssembly' doesn't exist`.

Captured evidence:
```
E ReactNativeJS: [Error: Uncaught (in promise, id: 0): "ReferenceError: Property 'WebAssembly' doesn't exist"]
I ReactNativeJS: M23B_RUNTIME_RESULT::{"ok":false,"hermes":true,"steps":[{"name":"slimdom compatibility init","ok":true},{"name":"loadForm representative fixture","ok":false}]}
```

### Root cause
The engine's XPath parser is `@getodk/tree-sitter-xpath` running through
`web-tree-sitter`, which is compiled to WebAssembly and loaded at runtime via
`WebAssembly.instantiate` (`tree-sitter.wasm`; 35 `WebAssembly.*` references in the
published bundle). **Hermes does not implement WebAssembly**, so the parser cannot
initialize on-device, and `loadForm` fails as soon as it needs to parse an XPath
expression.

This is independent of — and downstream from — the top-level-await packaging issue:
the TLA transform and DOM shim are necessary to even reach this point, but they are
not sufficient for end-to-end execution under Hermes.

### iOS
Not separately built. This is a Hermes-level limitation (no WebAssembly), not a
platform-specific one; iOS uses the same Hermes engine and fails at the identical
`WebAssembly.instantiate` step. A native iOS build was not spent to re-confirm a
Hermes-wide constraint (and the local CocoaPods issue remains).

### Revised interpretation
- Packaging/TLA question (the actual scope of M2.3b): **still GREEN** — solved with a
  small, deterministic, non-semantic transform + narrow alias.
- End-to-end "runs in a real app under Hermes" question: **RED** — blocked by the
  WebAssembly-based XPath parser, which no packaging transform or DOM shim can address.

### Recommendation (updated)
Direct-Hermes execution of the stock engine is **not viable** while the XPath parser
requires WebAssembly. Before/instead of M3, evaluate:
1. whether ODK can provide a non-WASM XPath parser path (or a JS/native tree-sitter
   binding) usable under Hermes; and/or
2. the hidden-WebView sidecar approach, where the WebView's JS engine provides
   WebAssembly and the engine can run unmodified.

The upstream TLA issue draft is still worth filing (it's a real, separate portability
blocker), but on its own it does not unblock React Native/Hermes.
