```json

  "type": "property",
  "rules": [{ "datasetProperty": "block", "actorProperty": "block" }]
```

  - A receives only `block=A` rows

- Verified runtime choices match filtered CSV row counts.
- Added cleanup/restoration in `finally` for dataset filter and actor-property state.

### M4.7.3 REST concurrency
- Added `updateEntity({ ..., baseVersion })` with explicit concurrency contract.
- Added dedicated client error code:
  - `ODK_CENTRAL_STALE_ENTITY_BASE_VERSION` (non-retryable).
- Live evidence:
  - correct `baseVersion` update succeeds (`N -> N+1`)
  - stale `baseVersion` rejected (HTTP 409; Central code `409.15`) and mapped to dedicated code.

### M4.7.4 version/conflict characterization
- Form-driven update generated by stock engine + OpenRosa submission, then REST-inspected.
- Observed ordinary online shape:
  - `version = N+1`
  - `baseVersion = N`
  - `branchId = null`
  - `trunkVersion = null`
  - `branchBaseVersion = null`
  - `conflictingProperties = null`
  - `conflict = null`

### M4.7.5 existing Entities offline
- Online prefetch of form + linked Entity CSV.
- Offline in-process cached-resource gate:
  - form loads from cached assets,
  - existing Entity can be selected,
  - derived fields + entity update block + local serialization all succeed.

### M4.7.6 locally-created offline characterization (no implementation)
- Runtime experiment:
  1. offline registration form serialization creates local Entity block (`create="1"`).
  2. observation form offline (backed only by cached CSV) does **not** include that new local Entity in choices.
- Result: no automatic cross-form propagation for offline-created entities without host-owned overlay/sync behavior.

- `odk-central-client` does not independently materialize/merge Entity state across offline forms.

---

## Gaps / future responsibility boundary (not implemented in M4.7)

To support cross-form visibility of offline-created Entities before sync, a future host-owned Offline Store/Sync Manager must provide at least:
1. Local Entity materialization from offline registration payloads.
2. A deterministic overlay/merge of local pending Entities onto linked Entity-List resources consumed by forms.
3. Version/baseVersion lineage handling for later server reconciliation.
4. Ordering/dependency policy between queued submissions and Entity visibility.

This belongs in the composition root/offline subsystem, **not** in `odk-central-client`, `odk-xforms-host`, or `odk-xforms-react`.
