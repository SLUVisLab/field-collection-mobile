## 4) Bridge protocol

Protocol is explicit JSON RPC:

- request:
  - `{ id, type, payload }`
- response:
  - `{ id, type: "response", ok, payload|error, latencyMs, startedAt, finishedAt }`
- event:
  - `{ type: "event", eventType, payload, emittedAt }`

Properties:

- deterministic serialization via stable key ordering in sidecar sender
- no ad hoc parsing
- structured error objects (`name`, `message`, `stack`)
- round-trip latency captured in host metrics

## 16) Compatibility-burden comparison

### Direct Hermes path

Required / encountered:

- `slimdom`
- selector adapter
- TLA transform
- Metro alias
- still blocked by Hermes WebAssembly gap for tree-sitter path

### WebView sidecar path

Required:

- hidden WebView
- small typed bridge
- stock `@getodk/xforms-engine` runtime in browser

Removable from production runtime path (if this architecture is adopted):

- `slimdom`
- selector shims
- generated TLA transform
- Metro xforms alias

Remaining bounded issue in this spike:

- WebView runtime lacked `crypto.randomUUID`; a tiny sidecar-local compatibility patch was added using `crypto.getRandomValues` to satisfy engine runtime expectations.

## 17) Verdict

**GREEN**

Why GREEN:

- Android and iOS runtime probes both pass initial + remount phases.
- All representative semantic checks pass (`calculate`, `relevant`, `constraint`, serialization, repeat).
- Bridge boundary remains clean and deterministic.

Remaining caveat:

- a small sidecar-local `crypto.randomUUID` shim is still required in this runtime.

## 18) Recommendation for M3

Proceed:

1. Keep `WebViewXFormsHost` as the leading architecture candidate.
2. Keep bridge payloads value/reference-only (no binary transport).
3. Proceed to M3 native/reactive UI integration against the `XFormsHost` boundary.
4. Keep the sidecar-local `crypto.randomUUID` shim tracked for possible removal/upstream alignment.
